# 测试情况与证据链分析

更新日期：2026-09-13。本文说明已实现功能如何测试、如何回归、结果从哪里取得，以及证据能够支持哪些结论。需求依据为《全双工语音打断实验（面试作业说明书）》及用户确认的家园交互规则。实现方案见 [实验报告](作业任务说明.md)，链路和状态机图见 [架构与状态机说明](架构与状态机说明.md)。

当前结论：旧 ASR `8k_zh` 的 60 个固定文本用例各测 3 次、5 个真实媒体场景全部通过；切换到 `16k_zh_en_2.0` 后，“直接切换并清旧缓存”真实媒体专项通过，本次本地回归也通过。新版 ASR 尚未重跑完整的五场景验收，不能把历史结果合并描述成新版全量通过。

## 1. 作业要求与验证方法

| 要求或风险 | 验证方法与判定依据 | 证据及范围 |
| --- | --- | --- |
| AI 播放时仍在接收用户语音 | 在旧轮 `speaking` 与取消之间收到新句的 ASR partial/final，并检查双向 RTP、下行非零能量 | 第 6 节真实媒体时间线；仅看累计包数不足以证明同时在线 |
| 疑似插话先 duck，不能立即硬切 | 解码服务端输出，比较 RMS；确认前播放队列继续消耗、旧 context 未取消，误触发后同轮恢复 | `TestDuckingReducesServerAudioAndContinuesPlayback`；实际幅度约为原来的 50% |
| 完整打断闭环 | 检查 duck、true、取消旧轮、清音频、切 epoch、新任务执行；对仍活跃的 LLM/TTS 分别断言 context 取消 | 第 6 节真实链路加并发单元测试，不用页面“已停止”代替后端验证 |
| 等待触发句 final 后回答 | partial 确认先预留新轮，final 前下行静音且不启动新生成；同一输入的 final 才启动回答 | `TestFullClosedLoopStartsNewGenerationOnlyAfterFinal`；与仅 final 路径分别测试 |
| 误触发与恢复 | 不稳定 partial、VAD 无文本、ASR 故障恢复音量；语气词、否定、引用由语义分类判 false | 自动测试覆盖控制逻辑和固定文本，尚缺系统性的真人回声/咳嗽样本 |
| 旧轮不能复活 | 清除待播帧，迟到音频被拒绝，旧 epoch 不再出现 speaking/completed；旧缓存输入 ID 不再派发 | 清缓存媒体场景加迟到结果单元测试 |
| 延迟、误打断、漏打断 | 固定预期标签与分母；分开统计直接响应、打断后响应、缓存等待 | 第 5、7 节；属于 Word 可选的体验验证，不声称线上准确率 |
| 失败案例与反思 | 保留历史错误、复现方式、修复和未覆盖边界 | 第 8 节；原始响应未留存时明确说明 |
| 演示过程记录 | 真人录制应关联播放、插话、duck、确认、停止和新轮回答 | [打断过程记录](打断过程记录.md)仍留空，本文自动化日志不替代待补录制 |

Word 建议的半双工/全双工、硬切/两阶段对照属于可选体验对比。目前没有控制变量的 A/B 结果；早期 20% duck 与当前 50% 的不同测试不构成对照实验。

## 2. 测试分层与替身边界

| 层次 | 输入和依赖 | 可以证明 | 不能单独证明 |
| --- | --- | --- | --- |
| Go 单元与组件测试 | 构造 PCM/ASR 事件、可控时钟、内存执行器或本地 HTTP/WebSocket 服务 | 取消传播、队列边界、协议解析、状态迁移、迟到结果隔离 | 云模型语义正确率、真实 ASR 和耳机听感 |
| 固定文本分类 | 固定文本、历史、当前工具和 partial/final，调用生产 DeepSeek 客户端 | 动作/打断标签与输出协议的回归 | ASR、partial 请求调度、动作内部重试、物理播放停止 |
| 真实媒体闭环 | 固定 WAV 经 WebAudio 虚拟麦克风进入浏览器；实际 WebRTC、腾讯 ASR、DeepSeek、腾讯流式 TTS | 真实云端识别、判定、取消、缓存和新轮下行的联动 | 真人麦克风、外放回声、物理耳机尾音 |
| 浏览器 UI 回归 | Playwright 加载页面，注入控制事件和长文本 | 控件、错误展示、静态图片、非空波形、响应式排版 | 云服务成功、真实录音或声学波形质量 |

媒体测试运行在 localhost，物理输出静音以避免外放反馈。输入是预合成语音，但处理链中的 ASR、意图判定和 TTS 都实际调用云服务；工具执行效果按当前需求以重复十次台词模拟，没有连接游戏客户端。单元测试中的替身仅用于可控地制造取消、拒绝和迟到回调，未冒充真实媒体演示。

## 3. 测试用例

### 3.1 固定文本集

完整定义见 [cases.json](../testdata/acceptance/cases.json)，版本 `home-acceptance-v1`，共 60 例。18 例动作分类覆盖基础动作、历史问题、问答边界、否定、引用和不支持的操作；42 例打断分类覆盖不同农务切换、同类重复、延后、问答、明确停止、语气词及 partial 完整度。每例具有固定 ID、上下文和预期，默认各执行 3 次。

以下为代表用例。打断用例除特别标注外均为 final；true 表示授权打断，false 表示保留当前播放，完整输入等待后续处理。

| 用例 ID | 当前活动与输入 | 预期 |
| --- | --- | --- |
| `action-water` / `action-plant-synonym` | “迪莫，你去浇下水。” / “帮我种地。” | `water` / `plant` |
| `action-praise-de` / `action-praise-de2` | 带历史的“干的不错。” / “干得不错。” | `affection`；媒体另验首次夸赞不失败 |
| `action-how` / `action-multi` | “怎么施肥？” / “先浇水再施肥。” | `general_qa`，不错误执行农务或多工具 |
| `action-unsupported` | “把来偷菜的人踢出去。” | `general_qa`，不执行未支持操作 |
| `switch-plant-fertilize` | 种菜中：“去施肥。” | true，无需附加“别种菜了” |
| `same-plant` | 种菜中：“去种地。” | false，同义动作不硬切 |
| `deferred-wait` / `deferred-suffix` | 浇水中：“等一下再去种地。”；种菜中：“去施肥，等种完再去。” | false，显式延后优先于隐含切换 |
| `praise-during-plant` / `question-during-plant` | 种菜中：“干的不错。” / “一加一等于几？” | false，普通夸赞和问答缓存 |
| `priority-question` / `priority-answer` | 种菜中：“先别种菜了，一加一等于几？” / “先回答我一加一等于几。” | true，明确暂停或提高回答优先级 |
| `stop-wait-final` / `stop-before-deferred` | 浇水中：“等一下。” / “别浇水了，等一下再去种地。” | true，完整停顿指令或明确停止优先 |
| `negate-switch` / `quote-stop` | 种菜中：“不要去施肥。”；问答中：“我刚才听到你说停一下这个词。” | false，否定和引用不当成命令 |
| `filler-en` / `filler-ah` | 种菜中：“嗯。” / “啊。” | false |
| `partial-complete` / `partial-incomplete` | 种菜中 partial：“去施肥” / “去施” | true / false；这里只测分类，不代表运行时收到任意 partial 就立即请求 |

### 3.2 五个真实媒体场景

场景定义见 [media.json](../testdata/acceptance/media.json)，执行脚本为 [verify_home.cjs](../scripts/verify_home.cjs)。每个场景均检查实际上下行媒体、非零下行音频及关键事件。

| 场景 ID / 参数 | 测试过程 | 核心通过条件 |
| --- | --- | --- |
| `deferred-wait` / `--wait` | 浇水中说“等一下再去种地” | false 后入队；浇水十次完成后才种菜十次；旧轮没有取消 |
| `first-praise` / `--praise` | 种菜中首次说“干得不错” | 不打断、不格式重试、不播报任务失败；完成后贴贴十次 |
| `explicit-replacement` / `--replacement` | 浇水中说“先别浇水了，去施肥”，随后夸赞 | 旧轮取消、待播清空；施肥完成后处理夸赞 |
| `direct-switch` / `--switch` | 种菜中直接说“去施肥”，随后问普通问题 | 无停止口令也切换；问题在施肥结束后回答 |
| `discard-old-buffer` / `--clear-buffer` | 种菜中先缓存问题，再切施肥，施肥中重新问问题 | 旧问题随打断丢弃；旧 epoch 不恢复；新问题独立缓存并正常回答 |

## 4. 如何做回归

### 4.1 本地快速回归

在项目根目录执行。Go 已加入 PATH 时直接用 `go`；本机安装位置为 `E:/go/bin/go.exe`。

```powershell
& 'E:/go/bin/go.exe' test -count=1 ./...
& 'E:/go/bin/go.exe' vet ./...
node --test scripts/acceptance_stats.test.cjs
```

`-count=1` 强制重新执行，避免把缓存结果误作本次运行。预期 Go 各含测试包为 `ok`、vet 退出 0 且无诊断、Node 为 4 pass / 0 fail。命令入口和 signaling 目前显示 `[no test files]`，不能称其拥有独立单元测试。未启用 CGO/C 编译器，未运行 race 检测。

UI 回归需要已启动的应用服务、Node.js 18 以上、Chrome 与 Playwright。脚本注入页面状态，不建立麦克风会话，不调用云接口。

```powershell
npm install --prefix bin/browser-check --no-save playwright
$env:NODE_PATH = (Resolve-Path 'bin/browser-check/node_modules').Path
$env:DEMO_URL = 'http://localhost:8080'
node scripts/verify_ui.cjs
```

预期返回 `passed:true`、五种宽度和 `controls:22`，截图保存到 `bin/ui/`。Chrome 路径不同可设置 `CHROME_PATH`。

### 4.2 完整固定验收

需要 `.env` 中有效的腾讯与 DeepSeek 配置、匹配引擎的 ASR 额度及 TTS 额度，会实际消耗云服务资源。沿用上面的浏览器依赖设置后执行：

```powershell
$env:GO_BIN = 'E:/go/bin/go.exe'
node scripts/verify_acceptance.cjs
```

默认运行 60 例 × 3 次文本分类和 5 场景 × 1 次媒体。脚本编译当前源码，自动选择空闲端口启动独立服务，结束时关闭；不需要替换正在使用的 8080 服务。输入 WAV 缺失时自动合成，已有素材复用。

```powershell
node scripts/verify_acceptance.cjs --text-only --repeat 1
node scripts/verify_acceptance.cjs --repeat 5 --media-repeat 3
```

每次结果位于新建的 `bin/acceptance/<UTC时间>-<进程ID>/`。先看 `report.md` 的通过/计划与失败项，再用 `summary.json` 看分类、分组延迟和配置，最后按用例 ID 到逐例结果、媒体 JSON、服务端日志及截图定位。目录还保存验收集快照、启动时 Git HEAD、源码摘要和实际 WAV 哈希；只对比提交号不足以排除未提交源码或输入素材变化。

单例失败后继续其他用例，保留已有证据；未执行、请求异常和不合法响应均不得算通过。全部计划断言通过才退出 0，否则非零。复跑应保留原失败目录，与新结果并排比较，不能覆盖后只展示成功一次。

### 4.3 定位问题时的最小回归范围

| 修改内容 | 必跑范围 |
| --- | --- |
| prompt、分类 schema 或模型 | Go 分类/对话测试、完整文本集，再跑受影响媒体场景；例如延后语义必须跑 `--wait` |
| duck、取消、输入缓存或 epoch | Go 对话、LLM、TTS、RTC 测试及全部五个媒体场景 |
| ASR 引擎、输入格式或协议 | 新旧协议测试、真实识别专项，再完整五场景检查 partial/final 变化；当前 V2 只完成专项 |
| 统计逻辑 | Node 统计测试，对保留的原始结果检查分母、去重和分组 |
| 前端样式或错误提示 | 五种尺寸 UI 回归；若改播放或停止逻辑，还需真实媒体与人工听测 |

单独复现“清旧缓存”可在一个未占用端口启动服务，例如终端 A 运行 `go run ./cmd/server -addr :8081`。终端 B 设置同样的 Node 依赖，然后运行：

```powershell
$env:DEMO_URL = 'http://localhost:8081'
$regressionDir = Join-Path 'bin' ('regression-' + (Get-Date -Format 'yyyyMMdd-HHmmssfff'))
$env:EVIDENCE_DIR = Join-Path $regressionDir 'evidence'
$env:SCREENSHOT_DIR = Join-Path $regressionDir 'screenshots'
& 'E:/go/bin/go.exe' run ./cmd/demo-fixtures -scene home-switch
node scripts/verify_home.cjs --clear-buffer
```

应用只有一个浏览器会话名额，媒体测试应连接独立服务，避免挤掉真人连接。其他四个场景的素材生成参数见 [其他技术说明](其他技术说明.md#历史问题与专项资料)。

V2 单次专项中，直接响应 final 到首音频为 1708ms；打断后新轮为 2306ms；新缓存问题为 19961ms。true 到取消事件为 133ms，触发句 final 到取消为 1084ms，第一条 partial 到取消为 2128ms。各路径仅 1 个样本，不据此计算有代表性的 P95，也不据两次不同测试判断新旧 ASR 的速度优劣。

## 6. 关键证据链分析

### 6.1 真实打断、旧缓存清理与新轮完成

来源：[V2 清缓存媒体 JSON](evidence/asr-v2-20260913/home-clear-buffer-voice.json)。以下均为 2026-09-13 UTC 时间，北京时间加 8 小时；`at` 是浏览器记录事件的时间。输入 ID 共用前缀 `26a331da-258b-4784-825c-aec5a0db61c6`，表中用 `:1`～`:4` 表示后缀，epoch 表示回答轮次。

| 时间 | 观察到的事件 | 含义 |
| --- | --- | --- |
| 03:16:39.226 | `asr_final :1`：“去种菜。” | 初始请求进入系统 |
| 03:16:40.244 / 40.675 | `plant running epoch=1` / `speaking` | 种菜台词开始下行 |
| 03:16:43.202 | `asr_final :2`：“1+1等于几？” | 旧轮播放中，识别仍能接收新输入 |
| 03:16:44.038 / 44.039 | `interrupt=false` / `input_buffered :2`，队列 1 | 普通问题等待 |
| 03:16:44.630 / 45.207 | 旧轮 `ducking` / `asr_partial :3`：“去” | 疑似新输入先降音，随后到达文本 |
| 03:16:46.251 / 46.316 | `asr_final :3`：“去施肥。” / `speaking reason=unconfirmed` | final 到达；未确认降音曾恢复，不能把这段画成持续 duck |
| 03:16:47.202 | `intent_result :3 interrupt=true latency_ms=921`，再次 `ducking` | LLM 授权切换，并保留确认前的降音阶段 |
| 03:16:47.335 | 队列变 0；`response_cancelled epoch=1 queue_dropped=250 tts_active=true` | 旧文本缓存和服务端待播清理；当时 TTS 仍活跃 |
| 03:16:47.336 | `plant cancelled`、`interrupted epoch=1`、`listening epoch=2`；`turn_transition previous_epoch=1 utterance_id=:3` | 取消与新轮绑定在同一触发句上 |
| 03:16:47.954 / 48.321 | `fertilize running epoch=2` / `speaking` | 新动作启动并下行 |
| 03:16:48.556 | 新轮指标 `asr_final_to_first_audio_ms=2306` | 已发送首个非静音帧；与 speaking 状态起点有区别 |
| 03:16:51.015 / 51.858 | `asr_final :4`：“1+1等于几？” / false 并缓存 | 打断后新说的问题正常接收 |

| 03:17:08.517 / 12.435 | `general_qa running epoch=3` / `completed` | 新问题完成回答，链路走到闭环终点 |

这条记录的关键判断如下：

- **全双工**：旧轮已开始播放且尚未取消时，`:2` 和 `:3` 仍有 ASR 结果。浏览器累计接收 1791 包、286560 字节，发送 1798 包、286400 字节，接收音频能量约 2.4743。包数和能量佐证媒体有效，时间线证明播放过程中上行仍在工作。
- **后端取消**：存在旧 epoch 的取消事件、250 个待播帧被清除、工具取消及新 epoch 转移；后续旧轮没有 speaking/completed。250 × 20ms = 5000ms 是丢弃的待播内容长度，不能解释成听到的停止延迟。
- **缓存确实丢弃**：旧问题 `:2` 进入过缓存，却没有后续 `input_dispatched`；被派发的是重新说出的 `:4`。只比较问题文本会把新问题误认成旧缓存复活，必须关联输入 ID。
- **取消的覆盖边界**：此处 `tts_active=true`，但没有 `llm_active=true`，固定动作文本的生成已结束。因此该实录不能证明当时两个云任务同时活跃并被取消；第 3.3 节的双活跃测试专门补足取消传播路径，LLM/TTS 客户端测试再验证连接能随 context 关闭。不能据此推断供应商内部计算和计费立即停止。
- **final 的先后关系**：这次 true 到达时 final 已有，所以新轮直接处理完整句。partial 确认早于 final 时的“先预留、再等待”由独立状态机测试验证，不能声称在本段真实录音中观察到了该顺序。

### 6.2 false 后恢复，完成当前任务再派发

来源：[完整基线的延后种地记录](evidence/acceptance-20260912/media/deferred-wait-1/home-wait-voice.json)，日期 2026-09-12、ASR `8k_zh`。UTC 时间链为：

`09:10:51.487 water speaking` → `09:10:53.937 final 等一下再去种地` → `09:10:54.436 interrupt=false` → `09:10:54.437 input_buffered` → `09:10:54.438 speaking reason=intent_deferred` → `09:11:10.668 water completed` → `09:11:10.670 input_dispatched` → `09:11:11.350 plant running` → `09:11:30.108 plant completed`。

原轮没有 `response_cancelled`，浇水与种菜都完成十次台词。这证明“确认 false”会恢复并等待，而不是静音后丢弃用户输入。这里十几秒的 final 到回答延迟主要是当前任务剩余播放时间，是预期排队行为。

### 6.3 严格 JSON、拒绝与兜底 false

生产链路为：DeepSeek JSON mode 及固定 prompt → 本地完整解析和字段校验 → 合法布尔结果，或错误兜底 false → `intent_result` 与日志 → 恢复播放、final 入缓存。模型输出文本不直接交给 TTS，也不从夹带文字的正文中抽取 JSON 来授权打断。

`TestIntentJSONIsStrict` 明确包含 `好的，{"interrupt":false}`，并覆盖围栏、重复键、额外字段、字符串布尔值和 null 等；这些响应不属于合法 false。`TestIntentRequestAndProviderValidation` 检查截断结束状态和非法正文的错误脱敏，`TestIntentErrorDefersInsteadOfInterrupting` 验证错误路径实际保留旧轮和输入。

事件携带 `interrupt=false fallback=true status=error`，reason 为 `invalid_output`、`timeout` 或 `request_failed`；日志记录 false、fallback、原因、epoch、输入 ID 和请求耗时，以区分异常和正常 false。统计脚本将异常算严格失败；即使它的 false 兜底碰巧符合预期，也不能提高通过率。这是协议防线与回归断言，不是“prompt 能绝对约束模型”的承诺。

拒绝覆盖需要进一步区分：文本式拒绝不符合 JSON 契约时会进入非法输出兜底；但当前 [意图客户端](../internal/llm/intent.go)没有单独解析供应商的 `message.refusal` 字段，也没有“refusal 与合法 content 同时出现”的专项测试。动作客户端的 refusal 测试不能代替意图客户端的覆盖，该组合应列为协议加固及补测项。

### 6.4 ASR 资源包问题的定位链

现象是页面反复显示识别连接失败，购买资源包后仍失败。诊断从服务端 ASR 4004 及实际请求引擎 `8k_zh` 入手，与用户购买的“大模型 2.0 实时语音识别”资源包类别对照，定位到计费类别不匹配。配置调整为 `16k_zh_en_2.0` 后还必须适配 V2 结果结构，不能只改引擎字符串。

验证分三步：协议测试确认签名包含 `input_sample_rate=8000`、上行仍为 3200 字节/200ms PCM16LE，V2 final 快照不会重复提交；4004 故障注入确认握手和识别阶段都有脱敏且可操作的提示；真实 V2 媒体记录确认连接成功并持续产出 partial/final，最终完成切换和回答。UI 回归另外检查错误原因可见，识别状态恢复后旧提示清除。

这支持已修复的引擎/协议和提示路径；不等同于测试了所有计费、鉴权或并发错误，也不保证今后账户额度不会再次耗尽。

## 7. 统计口径与结论边界

| 指标 | 计算口径 |
| --- | --- |
| 严格通过率 | 合法且标签正确的次数 / 计划次数；未执行、非法响应、超时均非通过 |
| 误打断率 | 预期 false、有效决策却为 true 的次数 / 已执行的预期 false 次数 |
| 漏打断率 | 预期 true、有效决策却为 false 的次数 / 已执行的预期 true 次数；错误兜底 false 计入漏判 |
| 请求错误率 | 请求错误次数 / 已执行次数；另保留只统计合法响应的混淆矩阵 |
| P50 / P95 | nearest-rank：排序后第 `ceil(p × N)` 项；0ms 有效，无样本为 null |
| final 到首音频 | final 进入服务端轮次管理器至首个非静音 RTP 帧发送，按每轮最后已知累计指标去重 |
| 句末到首音频 | ASR 句末偏移映射到输入包抵达服务端的时间，再计算至首个非静音 RTP 发送；缺失映射不编造数值 |
| `speech_to_duck_ms` | VAD 回推起点或 ASR 文本到达至首个非零降音帧发送；每轮只保留最近已知值 |
| 确认到取消 | 浏览器接收 true 与 response_cancelled 控制事件的时间差，含调度和事件传递影响 |

固定重复并非独立用户样本，“180 次分类全对”只说明这套输入的该次回归通过。文本 false/true 不直接等于真实语音的误/漏率，ASR 误识别及触发时机仍可能影响结果。旧基线 `speech_to_duck` 的直接响应 P50/P95 为 9/18ms，V2 单例中有 0/2ms；这些可能是 ASR 后再次降音的局部间隔，不能写成“用户开口几毫秒内系统就完成反应”。

`direct`、`interrupted`、`deferred` 必须分开；缓存保留原 final 时间，等待不应混入即时响应性能。`speaking` 事件也可能对应先发送的静音，首音频必须看非静音帧指标。当前指标均未量化从麦克风采集到耳机实际出声的总时延，事件层旧轮不恢复不等于已测出物理尾音长度。

## 8. 失败案例、反思与待验证项

| 问题 | 已有证据与修复 | 反思及边界 |
| --- | --- | --- |
| “等一下再去种地”误停浇水 | [历史文本](evidence/home-wait-classifier.json)与[语音](evidence/home-wait-voice.json)；等待类 partial 等 final，文本更新取消旧判定；固定 `deferred-wait` 回归通过 | 未完成句不能按停止前缀直接硬切；跨 ASR final 合并按用户决定未实现，仍可能受云端断句影响 |
| 首次“干的不错”提示任务没能启动 | [复现调查](evidence/home-praise-classifier.json)、[媒体](evidence/home-praise-voice.json)、[六工具协议验证](evidence/home-strict-classifier.json)；构造历史复现 schema 元信息进入参数，改用 strict 空对象加本地校验 | 原次完整模型返回未保留，只能说复现了同类协议错误；成功重试不能掩盖协议失败，首次夸赞媒体要求零重试 |
| 打断后旧缓存继续被回答 | [专项](evidence/home-clear-buffer-voice.json)及本次 V2 时间线；确认时清旧 final/草稿/请求并隔离迟到输入 | 只清音频不足以满足用户的“打断后缓存也不要”；需同时核对输入 ID 和 epoch |
| 买了 ASR 包仍识别失败 | 第 6.4 节计费类别、协议测试及真实连接恢复证据 | UI 应显示安全错误码和实际引擎，不能把额度、网络和鉴权都折叠成连接失败 |
| 未确认 duck 恢复后又降音 | V2 时间线在 03:16:46.316 恢复、47.202 再降音 | 当前 watchdog 与异步意图结果的交互会出现音量往返；可继续评估判定期间的恢复时机，同时保留噪声下的恢复上限 |

如果再投入一天，优先补齐当前 V2 配置的五场景完整回归，再录真人耳机与外放各一组，覆盖“停止”、普通问题、“嗯/啊”、咳嗽、背景声、短暂停顿和首音频刚开始时插话。用同一批输入保留成功与失败样本、输入 ID、epoch、控制日志及录音时间标记，才便于分析是 ASR、语义判定、取消调度还是播放缓冲造成问题。

尚未完成的验证包括系统性的真人噪声/回声、多说话人、首音频边界和短暂停顿媒体测试、物理尾音测量、长期弱网压力及 race 检测；意图响应的 `message.refusal` 处理与专门回归也待补齐。仅 final 触发和双任务活跃取消已有可控测试，但仍可补真实云服务的专门演示。对照实验属于可选扩展；游戏 SDK 和跨 final 合并属于未实现能力，不计作已完成验收。用户录制内容继续由 [打断过程记录](打断过程记录.md)另行承载。
