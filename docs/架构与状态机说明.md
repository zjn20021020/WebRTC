# 架构与状态机说明

交付 3 来自 `codex/aec-headphone-priority`，保留主分支的输入合并与顺序任务规划，并增加自动音频路由与手动兜底。以下图示对应生产 `AcceptASR` 入口；旧 `Accept` 的 partial 提前确认仅为兼容路径。

## 链路图

```mermaid
flowchart TB
  subgraph Setup[信令建连]
    Client[浏览器连接管理]
    Signal[Go 信令服务]
    Client -->|POST /api/offer| Signal
    Signal -->|SDP answer| Client
  end
  Signal -. 建立媒体会话 .-> Mic
  subgraph Conversation[双向媒体与推理]
    Mic[浏览器麦克风持续采集]
    Mode{自动识别或人工选择}
    Raw[耳机或未知设备 原音采集]
    AEC[扬声器 浏览器原生 AEC]
    RTP[Go 上行 PCMU 解码为 PCM16LE]
    ASR[腾讯实时 ASR 大模型 2.0]
    VAD[Go 能量 VAD]
    Manager[Go 轮次与打断管理]
    Intent[DeepSeek 打断判断]
    Relation[DeepSeek 缓存补充关系判断]
    Merge[跨 final 合并与来源去重]
    Action[DeepSeek 有序任务规划与本地校验]
    Plan[Go 计划调度 每步独立 epoch]
    Executor[Go 农务与亲密语音执行器]
    LLM[DeepSeek 迪莫角色问答]
    TTS[正文分句与腾讯流式 TTS]
    Queue[Go PCM 转 PCMU 与本轮待播队列]
    Gain[Go 正常增益或 50% duck]
    Speaker[浏览器远端音轨播放]
    Mic --> Mode
    Mode --> Raw
    Mode --> AEC
    Raw -->|WebRTC 上行| RTP
    AEC -->|WebRTC 上行| RTP
    Speaker -. 浏览器播放参考 .-> AEC
    RTP --> ASR
    RTP --> VAD
    ASR -->|partial / final| Merge
    Merge -->|草稿候选或完整逻辑输入| Manager
    VAD -->|疑似说话| Manager
    Manager -->|文本与当前工具| Intent
    Intent -->|严格布尔结果| Manager
    Manager -->|多条相邻缓存派发前| Relation
    Relation -->|true 合并原文 false 分别保留| Manager
    Manager -->|可处理的完整输入| Action
    Action -->|最多六步 顺序执行| Plan
    Plan -->|农务或亲密| Executor
    Plan -->|当前子问题| LLM
    Executor --> TTS
    LLM --> TTS
    TTS --> Queue
    Queue --> Gain
    Gain -->|WebRTC 下行| Speaker
    Queue -->|本步最后音频发送成功| Plan
  end
```

offer 和 answer 都在 ICE 收集完成后发送。音频走 WebRTC 音轨；浏览器通过 DataChannel 接收服务端的字幕、工具、打断和队列状态。上行不会因为旧轮生成、下行播放、duck 或确认打断而停止。媒体为 PCMU / 8kHz / 单声道，服务端与 ASR/TTS 之间使用 PCM16LE。

ASR 当前配置为 `16k_zh_en_2.0`，用 `input_sample_rate=8000` 声明实际输入，腾讯云完成升采样。新版 `sentences.sentence_list` 转为统一的 partial/final 事件后进入轮次管理器。

耳机和未知设备使用原音，关闭 `echoCancellation`、`noiseSuppression` 和 `autoGainControl`；扬声器仅开启 `echoCancellation`。页面默认自动识别，手动选择优先且本页重连后保留，恢复图标或刷新页面取消覆盖。模式控制采集处理，不改变系统实际播放设备；AEC 的物理外放效果仍待验证。

轮次管理器持有非打断输入缓存，并控制下行增益、任务上下文、剩余计划和待播队列。false 的完整输入在整份计划结束后派发；true 清旧输入、取消当前及剩余步骤并清待播。普通 final 收集 800ms，等待表达 1400ms；收集时只 duck，提交完整逻辑输入后才请求意图 LLM。完整限制见 [dev 说明](dev-跨final合并与任务规划.md)。

缓存派发前还会检查相邻未执行输入的补充关系。例如故事加主题限制会合成一次请求，独立问题仍按顺序保留。这次判断发生在分配新响应 epoch 之前，通过 `input_relation` 记录队列状态；它不属于当前回答的 `thinking` 状态，也不能授权打断。每次最多等待 2 秒，停止/断开会取消请求。原始字幕保留来源句，合并输入另列。

## 音频模式状态

```mermaid
stateDiagram-v2
  [*] --> automatic
  state "自动识别 未知时默认耳机" as automatic
  state "手动耳机 AEC 关闭" as headphones
  state "手动扬声器 AEC 开启" as speakers
  automatic --> headphones: 选择耳机
  automatic --> speakers: 选择扬声器
  headphones --> speakers: 选择扬声器
  speakers --> headphones: 选择耳机
  headphones --> automatic: 恢复自动或刷新页面
  speakers --> automatic: 恢复自动或刷新页面
```

模式状态与业务打断状态独立。连接中调整模式会请求新轨道，实际设置验证成功后替换发送轨和波形源，再停止旧轨；失败保留原轨，显示“设置未生效”。用户连续修改时作废过时结果。断开会停止采集和检测，但保留本页手动偏好；重连重新应用。细节见[音频路由与 AEC](自动音频路由与AEC.md)。

## 打断状态机

```mermaid
stateDiagram-v2
  [*] --> listening: 分配轮次
  listening --> thinking: 同句 final
  thinking --> synthesizing: 首段正文
  synthesizing --> speaking: 发送音频
  speaking --> ducking: 疑似插话
  ducking --> speaking: false 或超时恢复
  ducking --> interrupted: true 且门槛满足
  speaking --> completed: 生成与发送结束
  ducking --> completed: 未确认且自然完成
  interrupted --> listening: 新轮等待 final
  completed --> listening: 计划下一步或缓存或后续新输入
```

图示以播放中插话为主路径。生成（`thinking`）或合成（`synthesizing`）期间也可进入 `ducking`；它是叠加候选状态，期间原任务继续推进，恢复时回到当时的工作阶段，不会重新分类或重启旧回答。

语音确认打断后分配新轮；生产路径此时已取得合并后的 final，可以直接开始新请求。旧逻辑输入入口仍支持 partial 预留后等 final。手动停止也可取消尚在收集、还未分配轮次的输入。任务失败或 90 秒轮次超时从任意活动阶段进入 `failed` 并取消剩余计划。自然完成要求本轮生成已结束、音频全部发送且没有待实施的 true 确认。

初始 `ready` 表示空闲监听；页面在自然完成、失败或手动停止后可保持 `completed`、`failed`、`interrupted`，直到下个输入。断开会取消所有活动任务并关闭媒体会话。

单次 RTP 写入失败保留待发送帧供后续时钟重试，不立即变为 `failed`；取消轮次会一并清除这帧。图中展示服务可用时的业务状态，凭证未配置等启动条件见运行说明。

| 状态或事件 | 含义 |
| --- | --- |
| `listening` | 已分配当前轮次，等待触发句的 final |
| `thinking` | 正在分类工具或生成问答 |
| `synthesizing` | 已产出正文，正在获取合成音频 |
| `speaking` | 当前轮次处于音频播放阶段 |
| `ducking` | 疑似插话，音频按 50% 增益继续发送 |
| `interrupted` | 旧轮已停止 |
| `completed` | 本轮生成与音频发送结束 |
| `failed` | 当前任务因错误结束 |
| `intent_result` | 判定值、是否 fallback、请求耗时与原因 |
| `response_cancelled` | 旧轮取消、清除帧数、LLM/TTS 当时是否仍活动 |
| `turn_transition` | 旧、新 `response_epoch` 与保留的触发句 ID |
| `input_queue` | 待处理输入数量，确认打断清缓存时同步为零 |
| `input_merge` | 合并收集、提交或丢弃，携带所有 ASR 来源 ID |
| `input_relation` | 相邻缓存的补充关系、耗时与兜底；true 合并原文，false 保留两条 |
| `plan_status` | 整份计划状态、步骤序号和所有步骤的状态 |
| `plan_step_transition` | 自然完成后推进下一步，区别于语音打断切轮 |

## 跨 ASR final 输入状态机

```mermaid
stateDiagram-v2
  state "空收集器" as idle
  state "收集草稿，等待 final" as collecting
  state "已有 final，等待续句窗口" as waiting
  state "提交一条完整逻辑输入" as committed
  state "丢弃整组并记住来源 ID" as discarded
  [*] --> idle
  idle --> collecting: partial
  idle --> waiting: final
  collecting --> waiting: 全部草稿定稿
  waiting --> collecting: 同组续句 partial
  waiting --> waiting: 同组续句 final，更新窗口
  waiting --> committed: 800ms 或 1400ms 到期且完整
  waiting --> committed: 最长收集到期且完整
  collecting --> discarded: 最长收集到期仍缺 final
  collecting --> discarded: 越限或停止或识别失效
  waiting --> discarded: 越限或停止或识别失效
  committed --> idle
  discarded --> idle
```

普通 final 的续句窗口为 800ms，等待表达为 1400ms；首个 final 后最多收集 6 秒，尚无 final 时最多 15 秒。最多六个来源、2000 字符；同一 ASR 会话，时间戳可用时句间音频间隔不超过 1500ms 且不倒序。遇到来源边界，完整旧组先提交，不完整旧组丢弃，再开始新组。停止包括人工停止、确认打断和连接关闭。收集期间只形成候选 duck，不发起硬打断判定。

提交不等于立刻执行：当前有任务时先判定打断，false 的输入进入缓存。空闲派发前有第二阶段关系判断：

```mermaid
flowchart TD
  Idle[当前计划结束或空闲] --> Head{是否有相邻同会话缓存}
  Head -->|只有一条或来源不兼容| Dispatch[分配 epoch 并规划队首输入]
  Head -->|下一条尚为 partial| Wait[等 final 或输入收集超时]
  Wait --> Head
  Head -->|两条完整输入且可合并| Relation[关系 LLM 最多 2 秒]
  Relation -->|合法 true| Merge[拼接原文与来源 ID 移除第二条]
  Merge --> Head
  Relation -->|false 或错误| Dispatch
  Relation -->|停止 断开 确认打断| Cancel[取消判断并清理输入 迟到结果失效]
```

关系阶段错误记录 `fallback=true` 并保留两条输入；超出六来源或 2000 字符时也分别保留。它不能授权打断或追溯修改已开始的回答。`input_merge` 和 `input_relation` 将原始 ASR 来源连接到最终逻辑请求，详见[实验报告 D.7](作业任务说明.md#d7-跨-asr-final-合并)。

## 复合任务计划状态机

```mermaid
stateDiagram-v2
  state "规划并校验完整 execute_plan" as validating
  state "当前步骤执行与合成" as running
  state "当前步骤生成结束，等待发送完毕" as draining
  state "当前步骤完成" as stepDone
  state "整份计划完成" as completed
  state "当前及剩余步骤取消" as cancelled
  state "当前步骤失败，剩余步骤取消" as failed
  [*] --> validating
  validating --> running: 整份计划合法
  validating --> failed: 协议或请求最终失败，不执行步骤
  validating --> cancelled: 停止或上下文取消
  running --> draining: 生成结束
  draining --> stepDone: 待播及重试帧全部发送成功
  stepDone --> running: 还有步骤，分配下一 epoch
  stepDone --> completed: 已是最后步骤
  running --> cancelled: 确认打断或停止或断开
  draining --> cancelled: 确认打断或停止或断开
  running --> failed: 生成合成失败或轮次超时
  draining --> failed: 轮次超时
  completed --> [*]
  cancelled --> [*]
  failed --> [*]
```

图中校验阶段是请求生命周期，此时还没有已安装计划；失败只记录任务未启动。多步计划创建后，各步骤共享 `plan_id`，工具 ID 为计划 ID 加步骤序号，每步拥有独立 `response_epoch`。`tool_status` 记录当前工具，`plan_status` 记录整体及步骤快照，`plan_step_transition` 记录自然推进。单步请求沿用原工具生命周期。

自然推进复用已校验步骤，整份计划完成后才处理 false 缓存；硬打断取消旧计划及旧缓存，保留触发句启动新请求。异步结果必须通过 context/epoch 校验，旧计划不会重新安装。本步完成以最后 RTP 帧成功发送为界，不是物理耳机尾音回执。示例及边界见[实验报告 D.8](作业任务说明.md#d8-复合任务规划)。

## 确认打断时序

```mermaid
sequenceDiagram
  participant User as 玩家
  participant ASR as VAD 与 ASR
  participant Turn as 轮次管理器
  participant Intent as 意图 LLM
  participant Old as 工具与生成合成
  participant Audio as 下行队列与音轨
  User->>ASR: 旧轮播报中说新指令
  ASR->>Turn: 疑似说话或有效文本
  Turn->>Audio: 50% duck，继续发送
  ASR->>Turn: final 与窗口内的续句
  Turn->>Turn: 合并窗口到期且文本完整
  Turn->>Intent: 合并后的全文与当前工具
  alt 合法 true 且确认门槛满足
    Intent-->>Turn: interrupt=true
    Turn->>Turn: 保留触发句，清剩余计划与其他缓存草稿
    Turn->>Old: 取消旧轮上下文及请求
    Turn->>Audio: 清待播与重试帧，停止取旧音频
    Turn->>Turn: epoch 递增，进入 listening
    Turn->>Turn: 使用已提交的合并 final
    Turn->>Old: 在新轮启动分类与执行
    Old->>Audio: 新轮音频
  else 合法 false 或请求异常
    Intent-->>Turn: interrupt=false，异常标记 fallback
    Turn->>Audio: 恢复原音量
    Turn->>Turn: 缓存完整 final
    Audio-->>Turn: 当前计划所有步骤音频发送结束
    Turn->>Old: 按顺序处理缓存输入
  end
```

以上为设计时序，不是已录制的过程记录。具体阈值、取消边界与失败反思见 [实验报告](作业任务说明.md)，实现索引见 [其他技术说明](其他技术说明.md)。
