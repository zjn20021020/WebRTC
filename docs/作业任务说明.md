# 全双工语音打断实验报告

## 场景分析

本实验选择《洛克王国：世界》的家园管理助手。用户是正在管理家园的玩家，AI 是已经唤起的驻派精灵迪莫。驻派精灵看家、驱逐偷菜访客和种后浇水是用户提供的场景背景，本实验未接真实游戏客户端。

玩家通过语音请求浇水、种菜、收菜、施肥、亲密互动或通用问答。四类农务和亲密动作用固定台词重复十次模拟，问答正常生成。长时间执行过程中，玩家可能改变安排，也可能只是夸赞或提出稍后处理的问题。因此需要在 AI 播报时持续收听，区分应立即替换的请求与应延后处理的输入。

例如，浇水时说“别浇水了，去施肥”应停止浇水；施肥时说“迪莫你真棒”应保持施肥，结束后再贴贴。按键说话需要玩家额外操作，播完再听则会错过任务执行中的变更。本实验采用近全双工：上下行媒体同时工作，但语音断句、云服务处理、网络和播放缓冲仍带来延迟。

## WebRTC 链路

### 技术选择

| 环节 | 实现及理由 |
| --- | --- |
| 服务端与媒体 | Go + Pion WebRTC，单进程完成信令、音轨和轮次管理 |
| 信令 | 自定义 offer/answer，便于本地实验复现 |
| 编码 | PCMU / 8kHz / 单声道，与腾讯 ASR、TTS 的 8kHz PCM 直接衔接 |
| ASR | 腾讯实时 WebSocket `8k_zh`，持续返回 partial 和 final |
| LLM | DeepSeek `deepseek-v4-pro` 非思考模式，分别承担打断判定、工具分类和角色问答 |
| TTS | 腾讯 `TextToStreamAudioWS`，音频分片到达后即可入队播放 |
| 状态同步 | WebRTC DataChannel 发送字幕、状态、轮次、工具和打断事件 |

选择已有云服务，将实验工作集中于双向媒体、打断规则和取消闭环。PCMU 可以直接解码为 ASR 需要的 PCM16LE；TTS 也选 8kHz，当前链路无需重采样，但音质受窄带限制。

### 建连与上行

1. 浏览器申请麦克风权限，请求回声消除、降噪和自动增益。
2. 创建 `RTCPeerConnection`，添加麦克风音轨与 `control` DataChannel。
3. 创建 offer，等待 ICE 收集完成，调用 `POST /api/offer`。
4. Go/Pion 设置远端描述并生成 answer；浏览器设置 answer 后建立连接。
5. 服务端持续读取上行 RTP，将 PCMU 解码为 PCM16LE，分别用于能量 VAD 和腾讯 ASR。

ASR 按 200ms 音频分片持续接收数据，VAD 不截断其输入。AI 播报、降音和打断判断期间，麦克风与识别都保持工作。当前只维护一个浏览器会话，新连接会关闭旧连接；本地访问用 localhost，远程访问需要 HTTPS。

### 下行与轮次

完整输入交给动作分类器后，农务及亲密工具输出十次台词，通用问答加载迪莫角色规则并流式生成正文。正文按句提交 TTS，返回的 PCM16LE 分片转为 PCMU，经本轮待播队列送入同一条长期存在的下行音轨。

服务端每 20ms 发送一帧，最多缓存约 5 秒音频。无回答时发送静音保持音轨；队列满时限制合成推进，不阻塞上行收音。“当前任务完成”以生成结束且本轮音频全部发送为准，不以文本生成完为准，也不是耳机播放结束的精确回执。

完整链路图和状态转换图见 [架构与状态机说明](架构与状态机说明.md)。

## 打断状态机与规则

### 第一阶段：疑似插话

上行 PCM 的 RMS 连续约 200ms 超过 700，或另一句有效 ASR 文本到达后，进入 `ducking`。服务端将下行音频样本增益降至 50%，约 -6dB；旧轮生成、合成及队列继续运行。能量 VAD 用于较快降低音量，不能独立确认打断。

普通 partial 至少两个字符的共同前缀稳定约 200ms 后可以请求判定；明确停止表达可提前请求，final 使用完整文本判定。“等一下”“等会”“稍后”等等待类 partial 暂缓到 final，避免只听到半句话就停止旧任务。

### 第二阶段：确认与切换

独立 LLM 判断最新输入、是否 final、当前工具和对话上下文。只接受 `{"interrupt":true}` 或 `{"interrupt":false}`，本地严格校验完整响应。拒绝、非法输出、超时或请求失败兜底为 false，并记录 `fallback=true` 和原因。

| 当前活动 | 新输入 | 预期处理 |
| --- | --- | --- |
| 种菜 | 去施肥 | 确认打断，切换不同农务，无需停止口令 |
| 浇水 | 等一下再去种地 | 不打断，缓存到浇水结束 |
| 种菜 | 去种地 | 同类动作，不打断，按缓存规则处理 |
| 施肥 | 迪莫你真棒 | 不打断，缓存后贴贴 |
| 种菜 | 一加一等于几 | 不打断，缓存后回答 |
| 种菜 | 先别种菜了，回答我一加一等于几 | 确认打断，切到问答 |

合法 true 才能授权硬切。旧音频已开始播放时，至少保留 120ms 的 duck 阶段后实施；若旧轮尚在生成、未开始播放，则可直接取消。确认后依次完成：

1. 保留触发打断的句子，丢弃其他完整输入缓存和未完成草稿。
2. 取消旧轮上下文，结束仍活动的工具、LLM 请求、TTS WebSocket 和旧轮判定请求。
3. 清空旧待播音频和待重试帧，使后续下行不再取旧轮内容。
4. 递增 `response_epoch`，进入新轮 `listening`；收到触发句的 final 后分类并回答。若 final 已到达，则立即开始处理。

这一路径在服务端完成，不通过前端 `pause()` 代替取消。已到达浏览器抖动缓冲区的尾音不能靠清服务端队列撤回，目前未量化物理耳机残留。

### 非打断与恢复

合法 false 恢复正常音量，完整 final 进入 FIFO 缓存，旧任务音频发送完后再处理。partial 只更新草稿，不作为完整问题派发。确认被新文本撤回、判定失败或普通疑似插话不会提前清缓存。

没有有效确认时，VAD 检测到约 500ms 静音后再等待 800ms 恢复原音量；连续噪声最多保持 duck 4 秒。手动停止和断开也会清理待处理输入。ASR 不可用时解除未确认降音，避免声音持续变小。

### 轮次隔离

每轮拥有独立的上下文和音频队列。入队和发送前校验当前轮次及取消状态，旧结果无法重新进入活动队列；句子 ID 防止重复 final 再次执行。ASR 改写或追加文本会作废旧判定版本，已返回但尚未实施的确认可以撤回。被打断丢弃的输入也被记为已处理，迟到结果不能重新派发。

核心状态为 `listening`、`thinking`、`synthesizing`、`speaking`、`ducking` 和 `interrupted`；自然完成用 `completed` 表示，错误用 `failed` 表示。状态含义、转换条件及事件名见 [状态机说明](架构与状态机说明.md#打断状态机)。

## 运行方式

安装 Go 1.22 或以上，准备可用的腾讯 ASR/TTS 和 DeepSeek 凭证。获取项目：

```bash
git clone https://github.com/zjn20021020/WebRTC.git
cd WebRTC
go mod download
```

在项目根目录按 [.env.example](../.env.example) 建立 `.env`，填写腾讯 AppID、SecretId、SecretKey 与 DeepSeek API Key；模型为 `deepseek-v4-pro`，TTS 音色为 `101016`。然后运行：

```bash
go run ./cmd/server
```

浏览器打开 `http://localhost:8080`，连接并授权麦克风。页面由 Go 直接提供，无前端编译步骤。端口冲突时用 `go run ./cmd/server -addr :8081`。凭证只留在服务端，额度耗尽需恢复对应服务额度；完整配置步骤见 [README](../README.md#可复现运行方式)。

## 演示步骤

以下是录制时的操作顺序与预期现象，实际打断过程记录独立留在 [打断过程记录](打断过程记录.md)。

1. 启动服务，用耳机连接页面，确认麦克风波形、识别和声音输出正常。
2. 说“迪莫，你去浇下水”，观察识别字幕、浇水工具状态和“我正在浇水。”的连续播报。
3. 浇水播报中说“别浇水了，去施肥”。观察先降至 50% 音量，再停止浇水并切换轮次，随后开始“我正在施肥。”。
4. 施肥播报中说“迪莫你真棒”。观察短暂降音后继续施肥，待回答数量增加；施肥十次结束后再“贴贴。”十次。
5. 另起一轮说“去种菜”，播报中说“一加一等于几”，确认问题进入缓存；再说“去施肥”打断，确认旧问题被清掉。施肥过程中重新提出问题，新问题应在施肥完成后回答。
6. 观察全过程麦克风波形和识别仍工作；结束时点击“断开”。

## 失败案例与反思

### 等待安排被提前打断

“等一下再去种地”曾在 final 前就停止浇水。旧判定规则对“等一下”过于积极，补长文本也未充分作废旧请求。已改为等待类 partial 到 final 再判定，并在文本更新时撤销过时判定与尚未实施的确认。完整句的缓存路径已回归通过。

代价是单独说“等一下”暂停也需要等待 final。若 ASR 因长停顿先提交“等一下”、再提交“再去种地”，仍按两个句子处理；本次交付不做跨 final 合并，保留这一限制。

### 首次夸赞触发任务失败

“干的不错”曾正常进入缓存，却在派发时连续两次工具参数校验失败。用构造历史复现了模型将 schema 信息写入参数的同类错误：`{"additionalProperties":{}}`，而接口要求 `{}`。已启用官方 strict 工具模式，保留本地白名单、空参数校验和限次重试；首次夸赞完整语音回归通过。

这说明工具选择正确不等于调用协议正确，重试也不保证修复同一种格式错误。应将语义错误、协议错误和网络错误分别诊断，而非统一归因于用户说得不清楚。

### 噪声与回声

早期单频测试音曾被 ASR 转写成文字。能量阈值只能判断声音强弱，文字模型也无法直接判断声源。当前结合浏览器回声消除、两阶段降音、语义判断和未确认恢复，但未完成真人外放、咳嗽和不同设备的系统性对比。进一步改进应先采集声学测试样本，再评估专用 VAD 与回声抑制。

### 测试结论的边界

2026-09-12 固定验收中，180 次文本分类及五个真实云语音场景通过。媒体测试使用合成语音作为虚拟麦克风输入，主链路与打断控制使用实际服务；不代表已完成真人回声、弱网或耳机尾音验收。详细测试与实现资料归入 [其他技术说明](其他技术说明.md)。
